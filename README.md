# LeetCode Compass

> 一个用 Rust 编写的 LeetCode 学习伴侣桌面应用。
> 题库浏览 · 进度追踪 · 智能推荐 · 竞赛复盘 · AI 助理

---

## 1. 这是什么

LeetCode Compass 是一个**纯本地**的桌面工具，帮助你把 LeetCode 从"随机刷题"
变成"有方向地练"。它通过 LeetCode 的 GraphQL 接口读取你的公开数据，
在本地做分析和推荐，不需要部署服务端，也不上传任何数据。

五个功能页面：

| 页面 | 作用 |
|---|---|
| **题库** | 按题号列出全部题目（约 4000 题），显示难度、标签、完成状态；支持搜索、筛选、排序；点击任意行在浏览器打开题目 |
| **推荐** | 基于你的标签掌握度与完成情况，给出下一批该练的题，并附推荐理由 |
| **竞赛复盘** | Rating 走势、参赛频率、稳定性、逐场明细与文字总结 |
| **AI 助理** | 接入大模型 API Key 后，可就你的账号数据对话、提问、要建议 |
| **设置** | 绑定 LeetCode 账号、配置大模型、管理本地数据 |

## 2. 快速开始

### 2.1 环境要求

- Rust 工具链（`rustup` 安装即可）。项目声明 `rust-version = "1.75"`，开发验证使用 1.96.0。
- Windows 下使用 MSVC 目标（`x86_64-pc-windows-msvc`），需已安装 Visual Studio C++ 生成工具。
- **无需** CMake / NASM / OpenSSL（见 §5 技术说明）。

### 2.2 构建与运行

```bash
# 开发模式运行
cargo run

# 发布构建（约 5 分钟，首次编译需拉取并编译全部依赖）
cargo build --release
# 产物：target/release/leetcode-compass.exe（约 13 MB，单文件，无外部依赖）
```

### 2.3 首次使用建议顺序

1. 直接启动即可看到**题库页**——此时是**匿名模式**，题库、标签、难度分布
   全部可用，只是"完成状态"列显示为「未知」。
2. 进入**设置页**填入 LeetCode 用户名，点击保存 → 应用会拉取你的画像与
   技能标签统计，推荐功能随即启用。
3. （可选，强烈建议）填入会话凭据以解锁**逐题完成状态**，见 §3。
4. （可选）配置大模型 API Key 以启用 **AI 助理**。

## 3. 账号绑定与两档能力

LeetCode 的接口对"是否登录"返回的数据有实质区别，实测结论如下：

| 数据 | 匿名（仅用户名） | 需会话凭据 |
|---|---|---|
| 题库全量列表 | ✅ | ✅ |
| 各标签已解题数（推荐算法核心） | ✅ | ✅ |
| 全局难度分布 | ✅ | ✅ |
| 用户画像、解题总数 | ✅ | ✅ |
| **逐题完成状态** | ❌ 恒为 `null` | ✅ |
| 提交记录、提交日历 | ❌ | ✅ |
| 竞赛历史 | ⚠️ 部分可用 | ✅ 完整 |

因此应用采用**双轨降级**设计：未配凭据时功能完整可用，推荐算法自动回退到
「技能标签驱动」模式；配好凭据后自动升级为「进度感知」模式，推荐会更准
（能精确排除已完成的题、优先推错题）。

### 两站能力差异（重要）

国际站与中国站**不只是域名不同**——两站的 GraphQL schema 字段命名
系统性不同（例如国际站用 `matchedUser` / `questionFrontendId`，
中国站用 `userProfilePublicProfile` / `frontendQuestionId`）。
部分功能在中国站**没有对应的查询接口**，因此无法实现：

| 功能 | 国际站 `.com` | 中国站 `.cn` |
|---|---|---|
| 题库全量列表（含完成状态） | ✅ | ✅ |
| 账号画像（用户名、排名、声望） | ✅ | ✅ |
| 各难度已解 / 未解题数 | ✅ | ✅ |
| 全站题量统计 | ✅ | ❌ 接口不存在（改用题库总数替代） |
| 知识点（标签）统计 | ✅ | ❌ 接口不存在 |
| 提交日历 / 连续活跃天数 | ✅ | ❌ 接口不存在 |
| 竞赛复盘 | ✅ | ❌ 接口参数与字段均不同，未适配 |
| 最近提交记录 | ✅ | ❌ 提交节点缺关键字段 |

**影响**：中国站用户的推荐算法会降级为「基于题库元数据」
（难度、通过率、标签分布），仍可正常使用，但无法按知识点精准推荐。

> 若你需要完整功能，请在设置页把站点改为国际站 `leetcode.com` 并使用对应账号。
> 两站账号不通用，不能交叉使用。

#### 账号标识：两站的又一处差异

除了 schema 字段名，两站**"用什么去查一个用户"**也不一样：

| | 国际站 `.com` | 中国站 `.cn` |
|---|---|---|
| 查询参数 | `username` | `userSlug` |
| 取值 | 与个人主页 URL 一致 | **可能是 ASCII slug，与显示昵称不同** |
| 昵称可含中文 | 是 | 是 |
| 提交日历 / 标签统计 | ✅ | ❌ |

凭据后点「校验凭据」，会从登录态读出真实标识并回填。详见
§3「中国站：昵称 ≠ 账号标识」。

### 如何获取会话凭据

**第 0 步（最重要）：先确认你用的是哪个站。**

国际站 `leetcode.com` 与中国站 `leetcode.cn`（力扣）是**两套完全独立的账号体系**，
Cookie 互不通用。**选错站点会表现为「Cookie 总是无效」**，且很难自查。
所以：你的 Cookie 从哪个站复制的，设置页的「站点」就必须选哪个。

1. 浏览器登录 LeetCode（注意是 `.com` 还是 `.cn`）。
2. 按 **F12** 打开开发者工具 → **Network**（网络）→ 筛选 **Fetch/XHR**
   → 刷新页面 → 点击任意一个 `graphql` 请求。
3. 在 **Request Headers**（请求标头）中找到 **`Cookie`** 这一行，
   **复制整行的值**（形如 `LEETCODE_SESSION=...; csrftoken=...; _gid=...`）。
4. 回到设置页，选好「站点」，把整段粘进 **「整段 Cookie」** 框，
   点 **「自动提取」** —— 应用会自动分离出两个值，无需手工抠。
   也可以手工分别填入 `LEETCODE_SESSION` 与 `csrftoken` 两个输入框。
5. 点「保存」，再点「校验凭据」确认登录状态。

> **注意区分两处容易混淆的地方**：
> - 要复制的是 **Request Headers 里的 `Cookie`**，
>   **不是** Response Headers 里的 `Set-Cookie`，也不是 `CSRF-TOKEN` 请求头。
> - `csrftoken` 固定是 **32 位字母数字**。若长度不符，应用会直接提示——
>   这属于"格式错"，与"Cookie 过期"是两回事，别混为一谈。
> - 二者**必须成对提供**：LeetCode 会校验 `x-csrftoken` 请求头与 Cookie 值一致，
>   缺一个都会失败。

### 排查「Cookie 无效 / 过期」

按可能性从高到低检查：

| 症状 | 最可能的原因 | 处理 |
|---|---|---|
| 一直提示无效，从未成功过 | **站点选错了**（.cn 的 Cookie 发到了 .com） | 确认站点选择与实际 Cookie 来源一致 |
| 提示"值中出现了分号" | 把整段 Cookie 粘进了单个输入框 | 用「自动提取」按钮 |
| 提示"csrftoken 格式不符" | 复制成了 `CSRF-TOKEN` 请求头，或复制不全 | 重新从 Cookie 行复制 |
| 提示"未找到用户"（**中国站**） | 填的是**显示昵称**，而中国站按**账号标识（slug）**查询 | 见下方「中国站：昵称 ≠ 账号标识」 |
| 提示"未找到用户"（**国际站**） | **站点与账号不匹配**（拿 .cn 用户名查 .com） | 确认站点选择；错误信息里会显示当前站点 |
| 提示"请求不被接受（HTTP 400）" | 客户端请求了当前站点不存在的字段 | 一般是程序缺陷，错误信息会附上服务端原文，请反馈 |
| 之前能用，突然失效 | Cookie 真的过期了 | 重新执行上面第 2–4 步 |

> 补充：网页版还保持登录状态，**不代表** Cookie 仍然有效——服务端可能已轮换。
> 重新刷新页面、从最新的一次 `graphql` 请求里复制即可拿到新鲜值。

#### 中国站：昵称 ≠ 账号标识（重要）

力扣中国站的账号有**两个名字**，用途完全不同：

| | 示例 | 用途 |
|---|---|---|
| 显示昵称 | `梧糊` | 只在界面上展示，**可以随时改成中文** |
| 账号标识（slug） | `wuhu` | 注册时确定，用于查询与个人主页 URL |

中国站 `userProfilePublicProfile` 接口按 **slug** 查找。填昵称会返回
`null`，表现为"用户不存在"——**但拼写其实完全正确**，只是查错了字段。

**怎么找到自己的标识**：打开个人主页，URL 中 `/u/` 之后那一段就是：

```
https://leetcode.cn/u/wuhu/          →  标识是 wuhu，填 wuhu
https://leetcode.cn/u/梧糊/          →  ✗ 不是合法 URL，标识不可能是中文
```

**更省事的办法**：在设置页填好会话凭据，点「校验凭据」。应用会从登录态
自动读出真实标识并回填，你不需要自己查。之后刷新账号时，若发现标识与
昵称不一致，应用也会自动切换并提示。

> 国际站没有这个问题：它的 `username` 本身就是标识，与个人主页 URL
> 里那一段一致。

> ⚠️ **安全提示**：会话 Cookie 等价于你的登录态，泄露即可被他人完全冒充。
> 请只在本机使用，不要分享、不要截图、不要提交到任何仓库。
> 本应用将其以明文存于本地数据库（见 §6），这是当前版本的设计取舍。

## 4. 配置大模型（AI 助理）

在设置页配置以下字段：

| 字段 | 说明 |
|---|---|
| Provider | `OpenAI 兼容协议`（默认，覆盖绝大多数厂商）或 `Anthropic` |
| Base URL | API 根地址，**不含** `/chat/completions`。切换 Provider 会自动填入默认值 |
| Model | 模型名，如 `gpt-4o-mini` |
| API Key | 你的密钥 |
| Temperature | 采样温度，0.0–2.0，默认 0.3（分析类任务宜偏低） |
| Timeout | 单次请求超时秒数，默认 60 |
| 最大历史轮数 | 对话上下文裁剪上限，控制 token 消耗 |

常见配置示例：

```
OpenAI      : https://api.openai.com/v1          gpt-4o-mini
DeepSeek    : https://api.deepseek.com/v1        deepseek-chat
通义千问     : https://dashscope.aliyuncs.com/compatible-mode/v1   qwen-plus
Anthropic   : https://api.anthropic.com/v1       claude-sonnet-4-...（选 Anthropic Provider）
```

配置完成后可用设置页的「测试连通」按钮验证。错误会按类别提示：
401 鉴权失败 / 429 限流 / 超时 / 网络不可达。

> **API Key 是可选的。** 不启用 AI 功能时留空即可，保存不会被拒绝——
> 空配置表示"不启用 AI"，属于合法状态。界面上的 AI 助理页会提示未配置。

> AI 助理会把你的**账号统计摘要**（画像、技能标签、推荐结果、竞赛摘要）
> 作为上下文发送给所配置的模型服务。助理页面会明确列出"它当前知道哪些信息"，
> 便于你判断是否愿意发送。**不含**你的 Cookie 或 API Key。

## 5. 技术说明

### 5.1 技术栈

| 层次 | 选型 |
|---|---|
| GUI | `eframe` / `egui` 0.36.2（即时模式，纯 Rust 单二进制） |
| 异步 | `tokio` 1.53.1 |
| HTTP | `reqwest` 0.13.5（json / cookies / rustls / gzip / http2） |
| TLS | `rustls` 0.23.45 + `ring` 后端 |
| 存储 | `rusqlite` 0.40.2（bundled SQLite） |
| 序列化 | `serde` / `serde_json` |
| 中文字体 | 内嵌 SimHei（黑体，9.3 MB，见 §5.3） |

### 5.2 两处关键配置（改依赖前请先读）

**TLS 后端为何不用默认的 `aws-lc-rs`**
reqwest 的 `rustls` feature 默认拉入 `aws-lc-rs`，它需要 CMake + NASM + MSVC
编译 C/汇编代码，在部分 Windows 环境构建失败。因此改用
`rustls-no-provider` + `ring`（加密原语已预编译，无外部工具链依赖）。

**但 `rustls-no-provider` 意味着"没有任何默认加密后端"。**
必须在进程内显式注册，否则首次构造 `reqwest::Client` 时会
**panic（"No rustls crypto provider is configured"）**——注意这个错误
`cargo check` 和 `cargo build` 都发现不了，只在运行时炸。

注册代码已就位，改动相关依赖时**不要移除**：

```rust
// src/error.rs
pub fn install_crypto_provider() {
    let _ = rustls::crypto::ring::default_provider().install_default();
}
```

调用点有两处（幂等，保证 GUI 与测试路径都覆盖）：
`src/main.rs::main()` 首行、`src/leetcode/client.rs::LeetCodeClient::new()` 首行。

### 5.3 中文字体（若界面显示豆腐块请读这一节）

**症状**：界面上的汉字全部显示为方框（□），俗称"豆腐块"。

**根因**：egui 的 `default_fonts` feature 只内置拉丁字体（Ubuntu-Light、
NotoEmoji 等），**不含任何 CJK 字形**。中文必须由使用方自行提供字体文件。

**本项目的处理**：把黑体（SimHei）**内嵌进二进制**，
源码见 `src/fonts.rs`，字体文件位于 `assets/fonts/SimHei.ttf`。
在 `CompassApp::new()` 中通过 `crate::fonts::install(&cc.egui_ctx)` 注册，
**必须在 `configure_style()` 之前调用**（后者只设字号，不设字体数据）。

两个实现细节值得注意：

1. **中文字体是追加（`push`）到字体链末尾，而非替换。**
   egui 按字体链顺序查找字形，前面的字体优先。追加到末尾意味着
   拉丁字母与数字仍由 egui 内置字体渲染（字形更精致、数字对齐更好），
   只有内置字体缺失的汉字才回退到黑体。若直接替换，反而会降低英文显示质量。
2. **`Monospace` 字体族同样需要追加。** 代码块、题号等用等宽字体渲染，
   而内置等宽字体不含汉字，不追加同样会出豆腐块。

**为什么选黑体**：常见中文字体中体积最小（9.3 MB，对比微软雅黑 19 MB、
思源黑体 17 MB），且覆盖 GB2312 全集。黑体为无衬线，小字号下比宋体清晰。

**代价**：exe 体积由约 13 MB 增至约 22 MB。
换来的是**单文件在任意机器上都能正确显示中文，不依赖系统字体**。

**验证**：`cargo test fonts` 会跑一个端到端测试，它在离屏上下文中先断言
"egui 默认字体渲染不了中文"，再在 `install()` 之后断言"能渲染了"——
这是唯一能真正证明该问题已修复的测试。另有测试覆盖界面全部高频用字。

### 5.4 项目结构

```
assets/fonts/SimHei.ttf   内嵌中文字体（勿删）
tools/
├── regression_cn_400.py   真实接口回归：两站 schema 不兼容（HTTP 400）
└── regression_cn_slug.py  真实接口回归：昵称 ≠ 账号标识（slug）
src/
├── main.rs            入口：注册加密后端 → 启动 egui
├── app.rs             AppState / 页面路由 / 后台任务消息泵
├── fonts.rs           中文字体装载（防豆腐块）
├── models.rs          领域模型
├── config.rs          配置读写（含站点枚举与能力声明）
├── error.rs           错误类型 + 加密后端注册
├── storage/db.rs      SQLite：建表、迁移、仓储方法
├── leetcode/          GraphQL 客户端 / 双站点查询常量 / 响应 DTO
├── llm/               多 Provider 统一客户端 / 消息与工具类型
├── logic/             推荐引擎 / 竞赛分析 / 对话编排
└── ui/                五个页面 + 复用组件
```

**双站点适配的设计要点**：`config.rs` 的 `LeetCodeSite` 是站点选择的
唯一事实来源，同时声明各站点的**能力边界**（`supports_*` 方法）；
`leetcode/queries.rs` 为两站分别提供查询常量；
`leetcode/types.rs` 用 `serde alias` 让同一 DTO 兼容两站的字段命名；
`client.rs` 的 `current_site()` 决定运行时分派。
新增查询时必须同时考虑两站——`queries.rs` 中有双向回归测试锁死字段名。

**标识符与显示名分离**：`LoginIdentity` 把"用什么查"（`slug`）和
"叫什么"（`username`）分成两个字段。只要一个值会出现在请求参数里，
就不能假定它等于用户看到的名字——中国站是典型反例。
`refresh_account` 在成功路径上也会调用 `resolve_query_identifier()`
校正标识，避免"画像拿到了、其余查询用错标识"的静默半失效。

### 5.5 线程模型

UI 线程运行 egui 主循环，**从不做 I/O**。所有网络请求投递到 tokio runtime 的
后台任务，结果通过 `mpsc` channel 回传；UI 每帧以非阻塞 `try_recv` 消费消息，
有结果时调用 `request_repaint()` 唤醒重绘。这样即使请求很慢，界面也不会卡。

## 6. 本地数据与隐私

- 数据位置：`%APPDATA%\LeetCodeCompass\compass.db`（Windows）。
  若 `APPDATA` 不可用则回退至当前目录。删掉该文件等于重置全部本地状态。
- 存储内容：题库缓存、标签统计、竞赛记录、设置（含凭据）、
  会话校验结论、推荐结果。
- **凭据以明文存储**。这是本地工具的最低可行方案，未做 OS 级密钥链集成。
  请自行确保机器与账号安全。
- 应用**不会**上传任何数据到除以下两者之外的地址：
  1. `leetcode.com`（读取你的公开/授权数据）；
  2. 你在设置中填写的 LLM API 地址（仅在你主动对话时发送账号统计摘要）。
- 应用**不实现**代码提交、在线判题、登录代理，因此不存在触发账号风控的写入行为。
  题库数据本地缓存，不会重复全量拉取。

### 哪些东西会被记住

应用会持久化两类**推导结论**，避免让你重复劳动：

| 内容 | 何时失效 |
|---|---|
| 会话校验结论（含账号标识） | 凭据变更（换账号 / 换 Cookie / 切站点）时自动作废 |
| 推荐结果 | 绑定账号变更时作废；数据更新后可手动重算 |

> 凭据指纹只用于判断"凭据是否被改过"，是短哈希而非凭据副本。
>
> 启动时会**后台静默复验**一次凭据：有效则静默（不弹提示），
> 失效才提醒你重新获取 Cookie。断网等网络故障**不会**清除已有结论。
